# Detection benchmark

_Generated by `BenchmarkTest` from real engine runs (ruleset `2026.11-r1`, engine 0.1.0). Do not edit by hand: `./gradlew :forensics:testDebugUnitTest --tests '*BenchmarkTest*' -Dbenchmark.write=true` regenerates it, and the test fails if this file drifts from the code._

## How to read this

* Every file below was made by a **real tool** (LibreOffice round trips, PyMuPDF edits, Pillow/img2pdf scans, pyHanko signatures); none is a hand-faked artefact. The generators are in `tools/fixtures/`.
* **Ground truth** is known because the author made the alteration. *Without original* = the file alone (no reference supplied). *With original* = the trusted original supplied as reference.
* A file counts as **flagged** when its report category is *Confirmed change* or *Suspicious indicators*. TP/FP/TN/FN are computed against ground truth at that level.
* **Sample size is tiny and constructed by the author.** These are demonstrations of what each mechanism can and cannot see, not accuracy statistics. No percentages are given because none would be calibrated.
* **Microsoft Word was not available.** Scenarios B–E use LibreOffice (import PDF → .docx → export PDF) as the word-processor stand-in. Word-specific tool labels are tested at string level only.

**Counts (not rates):** without original — TP 10, FN 8, TN 13, FP 1; with trusted original — TP 18, FN 0, TN 12, FP 1.

**What the pattern shows.** Without an original the engine detects edits that leave *structural* evidence (kept revision history, covered text, overlays on scans, broken or post-signature changes, grain-free patches) and misses edits that leave none (a name or amount changed in a Word round trip, a regenerated PDF, a same-quality re-saved scan, a valid signature over false content). Supplying a trusted original converts those misses into located, confirmed differences, and never turns a harmless re-export into a confirmed change.

## Cases the engine does not support

* **Proving a PDF→Word→PDF round trip.** Nothing in the output file reliably records it; only tool labels (informational) can hint at it. Without a trusted original, content changes made this way cannot be detected (scenarios C, D).
* **Recovering history from a fully regenerated or rewritten PDF** (scenarios Fb, I): the history does not exist in the file. This is reported as *unavailable*, never as *no tampering*.
* **Judging truth.** Neither a valid signature, a matching hash, a matching issuer record nor an absence of indicators shows that information in a document is true.
* **OCR / text comparison of scans.** Scanned pages are compared only as rendered pictures (indicators), never as text.
* **Double-JPEG / DCT-coefficient analysis, JPEG block-grid misalignment, resampling detection, clone-detection and machine-learning forgery detectors.** Not implemented; image checks are limited to those listed above.
* **Online certificate revocation.** The app has no network permission. Revocation is evaluated only from CRL/OCSP data embedded in the file or the signature; otherwise it is reported *unknown*.
* **Legacy `adbe.x509.rsa_sha1` signatures and algorithms the platform cannot process** are reported as *could not be verified*, not as valid or invalid.
* **Trust lists used for PDFs in practice (Adobe AATL, EU trusted lists).** Only the device's certificate store (or a test CA in tests) is used, so legitimate signatures can show as *unknown root*.
* **Encrypted PDFs.** Structure is examined; strings, metadata and streams are not. Reported as a limitation.
* **Vertical or rotated text, and multi-column reading order,** in word reconstruction. Comparisons are consistent between two files extracted the same way but can differ across very different layouts.
* **DOCX originals as visual references.** A .docx can be compared by text, entities and embedded pictures, not by rendered pages.
* **Running on a physical device or emulator.** The APK is built and its UI is exercised by Robolectric tests, but no emulator was available in the build environment; `PdfRenderer` page rendering was not executed on Android (the visual-comparison algorithm itself is tested with a `pdftoppm` renderer).

## Evaluated and rejected

* **Error-level analysis (ELA).** Implemented with detail-stratified baselines and agreement across three re-encode qualities, then evaluated on the scan fixtures: it flagged 28–34 regions on *every* scan, including unedited controls, so it carried no discriminating information. It was removed rather than shipped as an indicator that cries wolf.
* **Noise analysis grid size.** The first version used 32 px blocks and missed the small flat patch in `Gh`; it was changed to 16 px after inspecting that file. Because the parameter was adjusted after looking at one edited fixture, the false-positive rate of the noise check is only checked on a handful of unedited controls (`G0`, `Gh0`, `Gn0`, the photographs) and is otherwise unmeasured.
